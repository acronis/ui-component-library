The problem

Consistency stops at the component

The kit spent its consistency budget on components — tokens, primitives, composites, a rendered audit. But interfaces are still assembled the old way: an engineer opens a screen and hand-wires primitives to match a mockup.

every screen

🎲 A fresh act of composition

Each screen is a new chance to drift — mismatched control heights, two components for one job, off-grid layout, ad-hoc panels.

optional

🤷 Patterns aren't enforced

Composites and patterns exist, but their use is a matter of author discipline — and discipline doesn't scale across teams and time.

instructions

🌫️ Prompts drift

"Good enough AI instructions" are unbounded and probabilistic; a component is bounded and deterministic. Prose guidance degrades.

The unfinished half of the uikitless line: close the generation half and make the pattern the enforced unit.

The thesis

Screens are patterns, all the way down

Screen and app code may not reach for primitives directly. The pattern is the mandatory unit of screen construction — the same move composites made over primitives, lifted one tier.

Separation of concerns

Four roles, one artifact chain

PM

🎯 Intent & behavior

Requirements, states, data, rules of the flow → the screen.yaml state machine + data bindings.

Designer

🎨 Intent & discovery

Hierarchy and pattern discovery in Figma — a reference/discovery input, not the structural authority.

AI skill

🤖 Decouple & generate

/screen-from-spec turns the PRD into a pattern-composed spec and generates the implementation.

Kit

🧱 Catalog & grammar

Owns the pattern/composite catalog and the grammar that guarantees the look.

The PM writes logic once, in prose; the AI turns it into a spec; the kit guarantees the look. No one hand-masters primitives.

How it works

generate → lint → audit → regenerate

The verification loop — not the prompt — is what makes rules-driven consistency real. Generation is allowed to be imperfect because the gates hold the line.

1 · DECOUPLE
PRD → screen.yaml
regions bound to approved patterns + a state machine
→
2 · GENERATE
spec → screen
rendered from patterns/composites only
→
3 · LINT
require-pattern
rejects hand-wired primitives (ESLint)
→
4 · AUDIT
screen-audit
rendered pattern-conformance + grammar

Already prototyped and shown to hold the line on protection-dashboard and settings-form — it even caught bugs in its own detectors (contrast, hidden proxies).

Enforcement, not etiquette

Three gates + one escape hatch

schema

📐 Required pattern

A region declares a primary pattern (and may nest child patterns). The slug must resolve in the catalog.

static

🚫 require-pattern

ESLint on app code: assembling primitives into a region that matches a known pattern is an error that names the pattern to use.

rendered

🔎 pattern-conformance

A screen-audit detector: every region must structurally match its declared pattern's anatomy.

Escape hatch → graduation: no pattern fits? patternless: {reason} is a tracked, ledgered deviation that feeds the graduation pipeline. Escapes are finite, not a loophole.

Design ↔ code

The implementation can be rule-truer than the mockup

Mockups are human-authored and improvise. Treating the mockup as the source of truth re-imports that drift into code. So we invert the authority: the spec (patterns) is truth; the mockup is a discovery input.

improvisation

✅ Correct it

Snap the improvised layout onto the nearest approved pattern. The shipped screen is more consistent than the drawing.

new structure

🎓 Graduate it

A genuinely new shape becomes a pattern candidate — designer proposes, kit ratifies.

intended

📝 Override it

A real exception is a scoped, dated grammar override — auditable, never silent.

Figma becomes what it's good at — a place to discover patterns — without ever silently dictating a screen's anatomy.

Ratified decisions

The rules of the model

# Decision Chosen
D1 Region granularity Nested patterns — a region tree, not one-per-region
D2 Enforcement rollout New screens error; existing hand-built grandfathered as warnings
D3 PRD → spec contract Entities + states + data + actions + per-state acceptance criteria (the audit oracles)
D4 Pattern ownership Joint — designer proposes, kit maintainer ratifies
D5 Logic location Screen-local in stateMachine; cross-screen in app.yaml
