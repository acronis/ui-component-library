## 2. PACKAGING DEFECT (pre-existing, not U6's) — `@tanstack/react-virtual` is a devDependency

**`src/components/ui/tree/tree.tsx:8` already imports `useVirtualizer`**, and
`@tanstack/react-virtual` appears only in **`devDependencies`** of
`packages/ui-react/package.json`. `@tanstack/react-table`, the comparable case, is
in `dependencies`.

**Why this is not currently a broken consumer install:** the package is **not** in
`vite.lib.config.ts`'s `rollupOptions.external` list (`:32-46`), so Rollup resolves
and **inlines** it into the published bundle. So there is no
`Cannot find module` — which is exactly why it has gone unnoticed.

**What it does cost:** the published bundle carries a vendored copy of a
third-party library that consumers cannot dedupe, patch or version-align. A
consumer already using `@tanstack/react-virtual` ships two copies. `recharts` and
`@base-ui/react` are externalised precisely to avoid this; `react-virtual` is the
odd one out and it is undeclared as well.

**U6a adds a second import of it** (`data-table-body-window.ts`), so the vendored
copy grows rather than the situation staying static.

**Not fixed here.** `package.json` is in no unit's `Owns` list, and moving a
dependency tier plus possibly adding an external is a packaging decision with a
blast radius outside the table family. **Recommendation:** move it to
`dependencies` (matching `react-table`), and decide externalisation separately —
the two questions are independent and only the first is clearly right.

## 3. FOR U6b — what the DataGrid toolbar must expose (the concrete hand-off)

The team lead asked for this to be specified during U6a so the F3 hand-off is a
contract rather than a negotiation. Clause 3's fallback order is
**same-index → previous-last → toolbar → scroll container**, so the toolbar is the
third rung and needs to be *findable* and *focusable* from the controller's
reconcile path.

**Minimum contract — one focusable element, discoverable without a ref chain:**

1. `data-grid-toolbar.tsx` renders its row with a stable hook attribute:
   `data-slot="data-grid-toolbar"`. It must be present **whenever the toolbar
   renders at all**, including the bulk-actions variant, because the fallback runs
   at reconcile time and cannot know which variant is mounted.
2. Within it, **at least one element must be reachable by
   `[data-slot="data-grid-toolbar"] :is(button,[href],input,select,textarea,[tabindex]:not([tabindex="-1"]))`**
   — i.e. an ordinary focusable control. The toolbar already renders search and
   view-options controls, so in practice this holds; the requirement is that it
   **keeps** holding when every optional member is disabled. If a toolbar can render
   with no focusable child, it must instead carry `tabIndex={-1}` on the row itself
   so the rung is never a dead end.
3. **No new prop, no imperative handle, and no ref plumbing.** The fallback resolves
   by query from the table's own root at the moment it runs. That keeps the toolbar
   ignorant of virtualization, which is the only way this does not become a
   cross-unit coupling.

**What U6b must NOT assume:** that the toolbar is a sibling of the table in a fixed
position, or that it exists at all. `toolbar: false` is a supported configuration,
and the chain must fall through to the scroll container in that case rather than
stall.

## 4. U6a design, as far as it was taken

Not implemented — recorded so the next operator does not re-derive it.

**Config resolution.** `DataTableVirtualizationConfig` already exists in
`data-table-features/virtualization.ts` with `estimateRowHeight`, `measure`,
`overscan`, `scrollToIndex`. Defaults per `api.yaml:113-119`: **40px / `fixed` / 8**.
`scrollToIndex` currently reaches nothing and must either be wired in the seam or
removed — it is a rule-7 candidate as it stands.

**The precondition is a real development error, not a guess.**
`containerRef.current?.dataset.bounded === 'true'`. Virtualization without
`appearance.height`/`maxHeight` is an invalid combination (design §5.1), and F3 made
it observable on purpose. Report it once per mount, not per render.

**Supply `measureRow` in BOTH modes, and this is the non-obvious part.** The doc
says `undefined` means "do not measure", so the instinct is to omit it in `fixed`
mode. Do not: the seam needs the element↔index map for **focus clause 1**, and
`measureRow` is the only channel through which the view hands over row elements. In
`fixed` mode, record the element and skip the measurement.

**Focus clauses 1 and 2 are one mechanism, not two.**
- Track the display index whose element `contains(document.activeElement)`.
- When building the window, **extend the contiguous range** to include that index
  rather than appending it out of order — appending breaks both the flat index space
  and the spacer arithmetic, and the flatness is load-bearing for U4 and the tree.
- Extending is only safe within a **bounded** distance. Past that budget, drop the
  row and call `containerRef.current.focus()` (setting `tabIndex = -1` on the
  viewport first, imperatively — the seam holds that ref, so this needs no change to
  `table.tsx` or the view). **That handoff *is* clause 2** — "when pinning cannot
  retain it" is the same condition as "the pin budget is exhausted", which is why
  these must be built together rather than as separate features.
- The seam touches no state, so "without changing logical current row" is free.

**Browser verification is a requirement of this unit, not a nicety.** Scroll
geometry, sticky ancestors, stacking contexts and the overlay scrollbar are not
expressible as happy-dom assertions — F3 caught a real defect in a browser that no
unit test saw. Two specifics to check there: the overlay scrollbar floats over
content so an end-pinned column sits under it (geometry, not a defect), and
`ScrollBar` is `z-[60]` above the table's 10–50 ladder.
