## 4. What U7 changed outside its own module, and why

- **`data-grid-toolbar.tsx`** and **`data-grid-config/toolbar.tsx`** — the
  `toolbar.tsx` edit the ownership README assigns to U7 on the rule that the unit
  whose change requires it makes it. It was **not** only the resolved-shape change
  the README predicted: the search box drove `column.setFilterValue` on a single
  column, so a multi-column configuration could never have matched more than one
  column regardless of what the engine was told. It now drives the global filter,
  and the reset clears both kinds.

  diverge in *behaviour* deliberately.

## 5. Two findings worth carrying forward

**A silently-inert config path, caught by testing rather than by types.** The
config first reached the engine under a `filters` key. There is no such controller
option — the feature's config comes from the `filtering` option itself
(`objectConfig(options, 'filtering')`). Typecheck did not object, because an
unknown key inside a **conditional spread** escapes excess-property checking. Every
`controllerOptions` contribution in the registry has this exposure, so a wrong key
is a silent no-op rather than a compile error. The behavioural tests caught it; the
type system will not.

**Applying the standing ✓ check to U7's own inherited work.** `filtering.ts` was
marked as shipped wiring by F2 and was correct as far as it went — but its ✓ covered
the boolean form only, and the three faceted row models it needed were never
installed, so `getFacetedUniqueValues()` returned an empty map. That is consistent
with the pattern the other units found: the assessment matched the configuration
that had tests.
