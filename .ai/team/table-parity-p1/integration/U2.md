## 6. `data-grid-config/tree.ts` — finished module, PARKED (not in the tree)

Reverted to its template in the checkout. Reason, learned the hard way below:
the module, the `declare module` augmentation and the `index.ts` manifest line
are **one indivisible atom**. Declaring on `DataGridGroupedConfigMap` trips
`_AssertEveryConfigRegistered`; removing the augmentation then breaks the
module's own `props.tree` / `resolved.tree` references. There is no half state.

Lands in one change together with the chrome (`columns` + the `renderStatus`

```ts
import type { ReactNode } from 'react';

import type { DataTableTreeLoadEvent } from '../../data-table/data-table-tree';
import { defineDataGridConfig } from './registry';

// OWNERSHIP: **U2**. The `tree` behavior group (design §5.2).
//
// `tree` owns TanStack's single expand/collapse feature (ADR-0001), so unlike
// `detailExpansion` this group does drive the row model — through the DataTable
// `tree` config, never from here. The engine half is
// `../../data-table/data-table-features/tree.ts`; the request machine is
// `../../data-table/data-table-tree.ts`.
//
// **A tree descendant DOES consume a pagination slot** (ADR-0001 OQ-2), decided
// deliberately opposite to the detail answer: a descendant is a real record
// entering the row model, where a detail row is a presentation of a record already
// on the page. With `pageSize: 2` and an expanded parent holding two children the
// row model is `[parent, firstChild]` and the sibling root is displaced.
// Established by experiment, not assumed.
//
// ── Registering this group: declaring and registering are ONE change ─────────
//
// `_AssertEveryConfigRegistered` in `./index.ts` fails to compile while a group is
// declared on the registry maps but absent from the manifest array. Staging the
// manifest line for an integrator therefore leaves a window in which nobody in the
// checkout can typecheck — which is how the workspace went red once already. The
// owning unit applies both together: pull immediately before, append only, never
// reorder another module's line.
//
// ── NOT YET REGISTERED, deliberately ────────────────────────────────────────
//
// This module is complete for `resolve` and the engine-facing `controllerOptions`,
// and **incomplete for the two chrome contributions** (`columns`, and the
// `renderStatus` shell that `renderLoadError` fills). Registering it now would put
// a `tree` prop on `DataGridProps` whose `renderLoadError`, `indent` and `column`
// members reach nothing — the "declared but reaches nothing" defect this programme
// has hit four times. The manifest line lands in the same change as the chrome.

/** Design §5.2's default indentation per depth level, in px. */
export const DATA_GRID_TREE_DEFAULT_INDENT = 20;

/** What `renderLoadError` is told about the branch that failed. */
export interface DataGridTreeLoadErrorContext<TData> {
  readonly row: TData;
  readonly error: unknown;
  /** Re-issues the child request for this row. */
  readonly retry: () => void;
}

export interface DataGridTreeConfig<TData> {
  /** Statically-known children for a record. Required (design §5.2). */
  getChildren: (row: TData) => readonly TData[] | undefined;
  /**
   * Fetches children for a record that has none yet. Expanding a childless row is
   * what triggers it; each request is keyed and a superseded result is dropped, so
   * a slow first response cannot overwrite a newer one.
   */
  loadChildren?: (row: TData, requestKey: string) => Promise<readonly TData[]>;
  /** Indentation per depth level, in px. Defaults to 20. */
  indent?: number;
  /** Renders the failure state for a branch whose children could not load. */
  renderLoadError?: (context: DataGridTreeLoadErrorContext<TData>) => ReactNode;
  /**
   * Which column carries the disclosure and the indentation. Defaults to the
   * first data column.
   *
   * The disclosure is an **in-cell** control, not a system column of its own,
   * because indentation and disclosure have to move together and a fixed leading
   * column cannot indent. `anatomy.yaml:11` lists tree among the "system columns",
   * but that line is an enumeration rather than an order — it also lists `actions`,
   * whose placement is a runtime config — and `anatomy.yaml:104` describes
   * `tree-expander` only as a `button` part, claiming no column of its own. The
   * repo's own shipped tree pattern puts the chevron inside the name cell,
   * indented by depth.
   */
  column?: string;
  /**
   * Retain expanded ids that are absent after a data replacement instead of
   * pruning them.
   */
  reserve?: boolean;
}

export interface ResolvedDataGridTree<TData> {
  readonly enabled: boolean;
  readonly getChildren?: (row: TData) => readonly TData[] | undefined;
  readonly loadChildren?: (
    row: TData,
    requestKey: string
  ) => Promise<readonly TData[]>;
  readonly indent: number;
  readonly renderLoadError?: (
    context: DataGridTreeLoadErrorContext<TData>
  ) => ReactNode;
  readonly column?: string;
  readonly reserve: boolean;
  /** Observes each lazy-children transition; `callbacks.onTreeLoad` maps here. */
  readonly onLoad?: (event: DataTableTreeLoadEvent<TData>) => void;
}

// ── The augmentation lands with the manifest line, not before ────────────────
//
// It is tempting to declare the group now and register it later, and it does not
// work: **declaring on `DataGridGroupedConfigMap` is itself what trips
// `_AssertEveryConfigRegistered`.** Adding the block below without the manifest
// entry turns `./index.ts` red for everyone in the checkout — verified by doing
// exactly that, three paragraphs after documenting that it would happen.
//
// So the augmentation, the manifest line, and the chrome are ONE change. Verbatim,
// to be pasted back when the chrome lands:
//
//   declare module './registry' {
//     interface DataGridGroupedConfigMap<TData> {
//       tree: false | DataGridTreeConfig<TData>;
//     }
//     interface DataGridIdentityFreeMap<TData> {
//       // Expanded ids and per-row request status must survive a data change,
//       // which only a real row id can do (design §3.1).
//       tree: false;
//     }
//     interface DataGridResolvedConfigMap<TData> {
//       tree: ResolvedDataGridTree<TData>;
//     }
//   }
//
// `tree` is independent of `detailExpansion` — separate slice, separate callback,
// separate display-row kind (ADR-0001) — so both may be enabled at once.

export const treeConfig = defineDataGridConfig({
  key: 'tree',
  kind: 'grouped',
  aliases: [],

  resolve({ props }) {
    const warnings: string[] = [];
    const config =
      props.tree !== undefined && props.tree !== false ? props.tree : undefined;

    if (config !== undefined && config.getChildren === undefined) {
      warnings.push(
        'DataGrid: `tree.getChildren` is required; a tree group with no child accessor reveals nothing.'
      );
    }

    return {
      value: {
        enabled: config !== undefined,
        getChildren: config?.getChildren,
        loadChildren: config?.loadChildren,
        indent: config?.indent ?? DATA_GRID_TREE_DEFAULT_INDENT,
        renderLoadError: config?.renderLoadError,
        column: config?.column,
        reserve: config?.reserve ?? false,
      },
      warnings,
    };
  },

  controllerOptions({ resolved }) {
    const { enabled, getChildren, loadChildren, reserve } = resolved.tree;
    if (!enabled) {
      return {};
    }

    // `renderStatus` is deliberately absent until the chrome lands: it is the row
    // shell that `renderLoadError` fills, and the DataTable feature emits no status
    // display row at all without it — so nothing here is half-wired in the
    // meantime.
    return {
      tree: {
        ...(getChildren ? { getChildren } : {}),
        ...(loadChildren ? { loadChildren } : {}),
        reserve,
      },
    };
  },
});
```

## 8. OPEN DEFECT — lazily loaded children never enter the row model

Found by clean room at `ef59dcb` with U2's three uncommitted files copied in, so it
is **U2's, not a teammate's**. 7 of 9 assertions pass; the two failures are both
`Unable to find an element with the text: Fetched`.

**Root cause, read from the installed `@tanstack/table-core`, not inferred:**

```js
// build/lib/utils/getCoreRowModel.js:17
return table => utils.memo(() => [table.options.data], data => { … });
```

The core row model is memoized on **`data` identity alone**. `getSubRows` is only
re-walked when `data` changes identity. So the machine's `WeakMap` side-channel —
`childrenOf(record)` consulted from `getSubRows` — **cannot invalidate the memo**,
and fetched children never become rows however correct the fetch was.

What does work (and is asserted): the expand→fetch wire, `loadState` transitions,
per-row keying, the `tree-status` row rendering, the retry command re-issuing, and
stale rejection. Only the *arrival* of children is broken.

**The two-keyings decision is not the flaw** — status-by-row-id and
children-by-record-object are still the right answers to *what keys what*. The flaw
is the delivery route: a side-channel read from `getSubRows` cannot trigger a
re-walk.

Options, unranked, none verified:

1. Return a transformed `data` from the feature's `engineOptions` — the return type
   is `Partial<TableOptions<TData>>`, which includes `data`. Needs checking against
   how the controller's own `data` interacts with the composed spread, and whether
   the collision check fires.
2. Hold loaded children in React state that the controller feeds back into `data`,
   so identity changes on load. No `data` contribution point exists today.
3. Make lazy children caller-owned: `loadChildren` resolves, the caller merges into
   its own `data`. Works today, but moves stale rejection out of the library, which
   `behavior.md` assigns to it.

Whoever picks this up: run the clean room first to reproduce, then decide the route
before writing anything. The two failing assertions are already correct — they were
what found this.

## 9. `anatomy.yaml:104` / `:111` — the `aria-controls` correction (ruled: option 1)

The spec as written is not implementable: `:111` gives `tree-children` `element: tr`
and says "the region has the `${tableId}--tree--${rowId}` target", but **several
`<tr>`s cannot share one id**. `DataTableRowPresentation` having no `id` member is a
symptom, not the cause.

Ruled: **omit `aria-controls` on the tree expander.** `aria-expanded` carries the
disclosure semantics; `aria-controls` is optional in ARIA, weakly supported, and
pointing it at a transient status row would announce that the button controls a
loading message and then vanish. `<tbody>`-per-parent was rejected because
`bodyWindow.rows` is one flat index space that U6's spacers/`measureRow` and U4's
sticky headers are built on, splitting it makes that space discontinuous and
state-dependent, it needs F2's spine file with no `sectionPresentation` point, and
`<tbody>` is a CSS containment boundary that restarts `:nth-child` striping.

Replace `:104`'s `aria-controls` sentence:

```yaml
  - id: tree-expander
    element: button
    description: >-
      DataGrid-owned ButtonIcon/Collapsible disclosure with Spinner/Alert retry.
      `aria-expanded` reflects only state.treeExpanded, including lazy loading.
      No `aria-controls`: a tree parent discloses a VARIABLE set of sibling rows,
      and several <tr> elements cannot share one id. Detail expansion differs —
      it controls exactly one projected row, so it does emit `aria-controls`.
```

and `:111`'s target sentence:

```yaml
  - id: tree-children
    element: tr
    description: >-
      Target P1 descendant data rows for one tree parent. They are ordinary record
      rows at depth > 0, NOT a single addressable region — which is why the
      tree-expander emits no `aria-controls`. Not detail content.
```

## 11. Sizing `treegrid`, while it is fresh (task #44)

**It is not a U2-sized change; it is table-wide across two spine files nobody on this
unit owns.**

Closer than a cold estimate suggests, because the pieces exist: `DataTableView`
already has roving focus — `rowNavEnabled`, `currentRowId`, `tabIndex`, `aria-current`
and Up/Down/Home/End on the row. So the increment is roles plus level attributes plus
Left/Right collapse/expand.

But two things make it structural rather than additive:

1. **Row navigation is currently opt-in** (`currentRow` / `highlightCurrentRow`).
   `treegrid` requires row-level focus as *primary* navigation, always on — so it
   changes behaviour for every existing consumer, not just tree ones.
2. It needs `role="treegrid"` on the table element (F3's `table.tsx`) and
   `aria-expanded`/`aria-level`/`aria-setsize`/`aria-posinset` on rows plus the new
   key handling (F2's `data-table-view.tsx`). Neither is a feature-module
   contribution; `DataTableRowPresentation` exposes no `role` or `aria-*` member, and
   adding them would be a tenth contribution point.

So: moderate work, low risk technically, **but it re-opens two spine files and
changes shipped keyboard behaviour for every table.** That is a P2-shaped change, and
the P1 recommendation stands: ship the documented limitation.

## 12. Hunch on the two failing assertions — one concrete check first

Not a guess about the cause (§8 has it, read from source) but about the fix:

**Check the controller's spread order before choosing a route.** `engineOptions`
returns `Partial<TableOptions<TData>>`, which includes `data`. In
`data-table-controller.ts` the `useReactTable({…})` literal sets `data` explicitly
*and* spreads the composed feature options. **If the composed spread comes after the
explicit `data`, route 1 works with no new seam** — the tree module returns a `data`
array whose identity changes when the machine's `records` change, the core row model
memo invalidates, and `getSubRows` re-walks and finds the WeakMap entry.

If the explicit `data` wins, route 1 is dead and route 2 needs a `data` contribution
point — which is a tenth point and an escalation to F2, not a U2 decision.

Two things to watch either way:

- `composeEngineOptions` throws when two modules set the same key. Only `tree` would
  set `data`, so no collision today — but it makes `data` a contended key for any
  future feature, which is worth stating in the README if route 1 is taken.
- Returning a fresh `data` array on every render would rebuild the row model
  constantly. It must be memoized on the machine's records, not recreated.

The two failing assertions are already correct and should not be weakened — they are
what found this, and they will go green when the delivery route is fixed.

machine persists in the `WeakMap`, so `engineOptions` can read it on render 2+. Wrong,
for the reason CORRECTION 2 gives: the `WeakMap`'s key — the `Table` — is what is
unreachable, on every render. Read CORRECTION 2, not this.

Two measurements to attach to it, since both corrections reason rather than measure:

- **The TDZ is total, not first-render-only.** A probe in `engineOptions`' body calling
  `ctx.table()` in a try/catch reported **10 invocations, 10 × `ReferenceError: Cannot
  access 'table' before initialization`, 0 resolved**.
- **Nothing needs merging into `data`, and memoization is a cost concern only.**
  `getSubRows` already returns fetched children from inside the closure where the table
  exists, so a **shallow copy** of the caller's array is sufficient — and a clean-room
  probe returning a fresh array on *every* render passed all 18 assertions. Correction
  1's first trap is therefore about row-model churn, not correctness.

### §12 CORRECTION — supersedes the conclusion above

My original wording, *"if the composed spread comes after the explicit `data`, route 1
works with no new seam"*, was wrong: **that condition is necessary, not sufficient.**
Read the settled facts and the open question below rather than that sentence.

**Settled fact (measured by the team lead):** spread order favours route 1 —
`data-table-controller.ts:807` sets `data`, `:819` spreads `...composedEngineOptions`,
so a feature contribution *does* override. The check I predicted was the right one to
name; it is just not the whole test.

**The second condition:** route 1 needs the tree module to return a `data` array whose
identity changes with loaded children, which means reading the machine at
`engineOptions` time — and `composeEngineOptions` runs **before** `effects`. `data` is
a value, not a closure, so the thunk escape that rescues `renderContext` does not
apply. This is the ordering trap recorded for U10, biting one seam earlier.

**Why I believe it is still not fatal — verify, do not assume either way.** Loaded
children are held in `childrenRef`, a `useRef`, not in the memoized machine wrapper.
The ref object is stable for the controller's lifetime and every wrapper closes over
the same one, so a *stale* wrapper's `childrenOf` still reads current children:

- Render 1 — no machine in the `WeakMap`; `data` returned unchanged. Correct, nothing
  has loaded.
- `effects` (render 1) publishes the wrapper.
- Load resolves → `childrenRef.current.set(record, children)` **and** `setRecords` →
  re-render.
- Render 2 — `composeEngineOptions` reads the render-1 wrapper from the `WeakMap`;
  its `childrenOf` reads the **shared ref**, which now has the children.

So the machine is unreachable exactly once, when it has nothing to contribute. **This
is my analysis, not a measurement** — the discriminating experiment is: expand a
childless row, resolve the loader, and assert `table.options.data` identity changed on
the following render. Run that before choosing between route 1 and a tenth
contribution point.

**Three traps if route 1 is taken:** the merged array must be memoized on the machine's
records or the row model rebuilds every render; `data` becomes a contended
`composeEngineOptions` key, so a second feature returning it would throw; and the
first-render inert path must return the caller's `data` unchanged rather than an empty
array.

### §12 CORRECTION 2 — supersedes correction 1. The blocker is the KEY, not the ordering.

Team lead's diagnosis, and it is better than both of mine. Record this one.

**Settled facts.** (a) Spread order favours route 1: `data-table-controller.ts:807`
sets `data`, `:819` spreads `...composedEngineOptions`, so a feature contribution
overrides. (b) The machine does persist across renders. (c) **`engineOptions` still
cannot reach it.**

**Why (c).** `featureContext.table` (`:755`) is a thunk over `const table` declared
*later in the same function body* (`:806`). Each render creates a new binding, so
calling `ctx.table()` from a contribution point's **body** hits the temporal dead zone
for *that* render — it does not fall back to the previous render's table. That is
exactly why the controller's comment says composers must only build closures that call
it later. My `getSubRows` is safe because it is a callback; a `data` **value** is not.

**So the machine's `WeakMap` key — the `Table` — is unreachable at the only moment
route 1 needs it, on every render, not just the first.** My correction 1 was right that
the machine persists and wrong that it is therefore readable.

**The fix is a key available before `useReactTable` runs: `ctx.tableId`.** A stable
string, present in the base context, readable in `engineOptions`' body. Cost: a
`Map<string, Machine>` does not self-release like a `WeakMap` keyed by the table, so it
needs explicit cleanup on unmount — which `effects` can do.

That makes route 1 viable without a tenth contribution point, and it changes what
`data-table-tree.ts`'s publication mechanism should key on. The three traps in
correction 1 still apply.

## 13. What U2a landed, and what U2b is still holding

U2 was split. **U2a is the eager tree and it ships; U2b is lazy children and is
held** until the delivery mechanism above is productionised.

**Landed in the engine half** (`data-table-features/tree.ts` + its nine assertions):
`tree.getChildren` feeding `getSubRows` with the config route winning over the
caller's raw accessor; `getExpandedRowModel` gating; the `onExpandedChange` binding
with both unhoisted reads intact; sibling-scoped sort (a test, not code); tree
descendants consuming pagination slots; and the depth/indent row presentation.

**Deliberately NOT declared, and the reason is in the module header:**
`loadChildren`, `renderStatus`, `DataTableTreeStatusContext`, the `tree-status`
display row, `onLoad`, and a live `tree.loadState`. The `effects` machine wiring came
out with them. `../data-table-tree.ts` stays committed and unit-tested but
**unreferenced** until U2b — an orphan on purpose, not an oversight.

**One change of substance beyond the split.** `tree.indent` reached nothing at the
DataTable layer: `DATA_TABLE_TREE_DEFAULT_INDENT` had zero consumers, and
`--table-tree-depth` alone cannot produce a length without every consumer
hard-coding the step. `rowPresentation` now emits **both**
`--table-tree-depth` (unitless) and `--table-tree-indent` (a length), so the
documented direct-DataTable route resolves from one selector:

```css
padding-inline-start: calc(var(--table-tree-depth) * var(--table-tree-indent));
```

DataGrid's in-cell transform reads the same two properties, so the design §5.2
default lives in exactly one place. Asserted at a **non-default** step (32) first —
at 20 the assertion cannot distinguish a wired config from the fallback.

**The nested-namespace merge coverage moved rather than disappeared.** It was
asserted through `tree`'s `loadState` contribution, which U2a removes.
`detail-expansion` is now the only live nested contributor, so the assertion is
`detail.canExpand` (contributed) coexisting with `detail.isExpanded`/`toggle` (base).
Negative control: renaming `detail` in `NESTED_CONTEXT_NAMESPACES` turns exactly that
one assertion red and leaves the other eight green.

**All five negative controls fire**, each on the assertion it should: the nested
merge, the configured indent, the depth, the config `getChildren` route, and
`paginateExpandedRows`. The last two are broad rather than discriminating — they
change the row model, so they redden most of the file; recorded as such rather than
claimed as precise.
