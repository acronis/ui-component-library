## 1. `packages/ui-spec/components/data-grid/behavior.md` — one scenario to add

**Section:** `## Advanced parity`, immediately after the existing
"Row-click selection and indeterminate policy" scenario (`:124-133`).

**Why:** that scenario covers the indeterminate policy without saying which way it
defaults, and **the default was ruled against design §5.2** — it stays `true`
(select-all), matching what ships, because flipping it would change behaviour for
every existing caller with no code change on their part. A deviation with no
scenario is the shape a later reader "corrects" back to the document.

Add verbatim:

````
```gherkin
Scenario: [Target P0 — shipped legacy parity] The indeterminate default selects, and opting out clears
  Given multiple selection with selectAllOnIndeterminate unset
  When some but not all eligible rows are selected
  And the user activates the header select-all
  Then every eligible row is selected, which is the shipped default
  And an ineligible row is not selected
  When the same grid sets selectAllOnIndeterminate to false
  Then activating the indeterminate control clears the selection instead
```
````

**Also note for whoever reconciles the spec with design §5.2:** `api.yaml`'s
`selection` defaults line reads "reserve/range false" and says nothing about this
member's default, so **no `api.yaml` edit is needed for that** — the deviation lives
in the scenario above, the member's docblock, and the changeset.

## 1.1 `packages/ui-spec/components/data-grid/api.yaml` — one clause to add

**Section:** the `selection` entry's `description`, appended to the sentence that
already names `selectByRow`.

**Why this is a spec edit and not a note to us.** It is a caller-facing rough edge
in a published component, and a handoff document is read by this team, not by
callers. `api.yaml` is where the discouraged-combination rules already live, and
putting it there is the difference between a known limitation and a bug report in
six months.

Add:

```
        `selectByRow` combined with pointer activation is not recommended in
        `mode: 'single'`: a double-click toggles the row twice, so the net effect
        is an empty selection rather than the previously selected row. Multiple
        mode nets to no change, and keyboard activation never toggles.
```

## 1.2 `packages/ui-spec/components/data-grid/behavior.md` — the residual's scenario

**Section:** `## Advanced parity`, after the scenario in §1.

```
```gherkin
Scenario: [Target P0 — known limitation] Row-click selection and pointer activation in single mode
  Given single selection with selectByRow enabled and one row already selected
  When the user double-clicks a different row to activate it
  Then that row is toggled twice and the selection ends empty
  And the previously selected row is not restored
  And in multiple mode the same gesture leaves the selection unchanged
  And keyboard activation never toggles selection in either mode
```
```

**Why it ships rather than being fixed** (ruled): suppressing it means knowing
whether a click will become a double-click, which means **delaying every selection
in every configuration** to smooth one combination's edge. That cost is paid by
every caller; the residual is paid by callers who opt into two members at once in
single mode.

**Not staged, deliberately:** no `index.yaml` edit. U9 changes no component's
`status:` or `since:`, and per NB-4 no unit touches an `index.yaml` regardless.

## 2. `data-table-view.tsx` — the `selectByRow` consumer member

Not an integration-queue edit; recorded here because it is the one part of U9 that
needed a file U9 does not own, and the reason generalises.

`selectByRow` needs a **row-level** click handler. Of the nine DataTable
contribution points and the six DataGrid ones, none reaches one:
`rowPresentation` carries `className`/`style`/`expanded`/`sticky`/`stickyOffset`
and no handlers, and a record row's remaining props come from the view alone. The
only route is `viewProps` → `onRowClick`, which `row-interaction.ts` already
claims — and `composeViewProps` collision-checks every defined key, so a second
claimant **throws at render** rather than losing quietly. It is reachable from a
legitimate config (`selection={{ selectByRow: true }}` with
`rowInteraction={{ onClick }}`), so contributing that key would have shipped a
crash, not a limit.

### 2.1 RESOLVED — the edit was granted and `selectByRow` shipped in `7a736f7`

The four-point patch in §3.1 landed in `data-table-view.tsx` with the team lead's
grant, and F2 was sent the diff after the fact rather than blocking before it. The
assertions are live in
`packages/ui-react/src/components/ui/data-grid/__tests__/data-grid-select-by-row.test.tsx`;
nothing is parked any more, and the `.pending` file that briefly held them is gone.

**Two things from the interval are worth keeping**, because they are about the rules
rather than about this member.

**A red type assertion is not the same cost as a red runtime assertion.** The
standing rule is "never `.skip`; hold a failing test red and uncommitted instead",
and its purpose is met either way — but `tsc` compiles untracked files in `src/`
just like tracked ones, so four `'selectByRow' does not exist` errors sat in the
workspace typecheck that every unit runs as its self-check. Not a commit block (the
pre-commit hook runs `lint-staged` only, whatever `AGENTS.md:253` says), but an
attribution tax on four other people. The amended rule, now ratified: **hold a
failing runtime assertion red and in place; hold a failing *type* assertion out of
the compiled tree, with the restore command recorded.**

The rejected alternative was to keep it in `src/` and cast the config
(`...({ selectByRow: true } as object)`) to quiet `tsc`. A cast is the shape of a
suppression, and it would have left three red tests in a shared checkout in a
programme that has lost hours to misattributed failures.

### 2.2 The two spine-edit properties, asserted rather than assumed

Both were questions the team lead raised before granting, and both are now tests in
`data-grid-select-by-row.test.tsx` under
`describe('DataGrid selection — what selectByRow does not change')`.

**`isInteractive` gates exactly two things** — the row's `onClick` (`:419`) and
`cursor-pointer` (`:479`). `tabIndex` and `onKeyDown` are gated by `rowNavEnabled`
instead, so widening `isInteractive` gives the row **no tab stop and no keyboard
binding**. That is what keeps the checkbox the accessible primary control: a
focusable row with no role would be the opposite of the stated intent.

**`handleRowClick` does fire on the pointer activation path.** A double-click
dispatches click, click, dblclick, so the handler runs **twice** before
`onRowActivate`, and the two toggles net to no change — double-clicking to open
leaves selection where it was. Asserted from both a selected and an unselected
start, so the pinned invariant is "net zero" and not "ends up deselected". Enter
activation does **not** go through `handleRowClick` at all (it is on the row's
`onKeyDown`), so it never toggles.

**One residual, in single mode, ruled ship-it — and its record lives in the spec,
not here.** See §1.1 and §1.2: a handoff document is read by this team, whereas this
is a caller-facing rough edge in a published component, so `api.yaml` and
`behavior.md` are the right homes and the staged blocks carry the whole
description. Noted here only so a reader of this file knows it exists and where it
went.

## 3. Why `selectByRow`'s consumer member was missing at all

§1.7's sweep records `DataTableViewProps` (U9) as closed by the `viewProps` point.
That holds for the appearance cluster because F2 pre-declared those props. It did
not hold here, and the reason is worth keeping: **the plan of record said
`selectByRow` shipped in P0.5, so F2 had no reason to pre-declare a consumer
member for it.** A false status does not only mislead a schedule — it removes
members from other units' pre-declaration lists, which is where the cost lands.
Escalated to the team lead rather than routed around (task #54 tracks the wider
audit).

### 3.1 The patch, verbatim — 4 points, all additive, all in `data-table-view.tsx`

**(a)** On `DataTableViewProps`, next to `onRowClick` (`:95`):

```ts
  /**
   * A body-row click toggles that row's selection. The selection checkbox stays
   * the accessible primary control; a descendant that stops propagation (the row
   * checkbox, an action button, the detail expander) does not reach this.
   * Ineligible rows are skipped via `row.getCanSelect()`, and single-selection
   * mode replaces rather than accumulates, both from the engine.
   */
  readonly selectByRow?: boolean;
```

**(b)** In the destructure (beside `currentRow = false`, `:191`):

```ts
    selectByRow = false,
```

**(c)** In `handleRowClick` (`:379-384`) — **between** the roving-focus write and
`onRowClick`, so a caller's handler still observes the post-toggle state:

```ts
    const handleRowClick = (event: ReactMouseEvent<HTMLTableRowElement>) => {
      if (rowNavEnabled) {
        controller.requestChange('currentRowId', row.id as RowId, 'pointer');
      }
      if (selectByRow && row.getCanSelect()) {
        row.toggleSelected();
      }
      onRowClick?.({ row: rowContext, nativeEvent: event });
    };
```

**(d)** `isInteractive` (`:377-378`), which also gives the row `cursor-pointer`:

```ts
    const isInteractive =
      rowNavEnabled ||
      selectByRow ||
      onRowClick !== undefined ||
      onRowActivate !== undefined;
```

Then, in `data-grid-config/selection.tsx` (U9's, no coordination needed):

```ts
  viewProps({ resolved }) {
    const { enabled, selectByRow } = resolved.selection;
    return { selectByRow: enabled && selectByRow ? true : undefined };
  },
```

`undefined` rather than `false` so the composer skips the key entirely — a module
that conditionally opts out returns `undefined` for the point rather than omitting
it, and nobody else claims `selectByRow`, so there is no collision either way.

**Keyboard is deliberately out of scope.** The scenario says "clicks a body row",
and the row's `onKeyDown` already maps Enter to activation. Mapping Space to select
would be an invention, not parity — and it would collide with Space on a focused
row inside a scroll container.
